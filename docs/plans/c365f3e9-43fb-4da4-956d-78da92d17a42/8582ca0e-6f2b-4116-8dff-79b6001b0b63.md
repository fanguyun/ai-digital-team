## 2. 方案设计（关键取舍与备选）

### 2.1 核心方式：同一任务，多轮执行

沿用现有 `Task → TaskRun` 关系：

- `Task` 表示用户持续推进的目标。
- 每次成功派发新增一个 `TaskRun`。
- 原运行的状态、摘要、日志和消耗统计保留。
- 再次发起后，任务卡显示最新一轮的状态。

状态变化如下：

```text
已完成 DONE
  ├─ 编辑并保存 → DONE，提示“需求已更新，可再次发起”
  └─ 确认再次发起
       ├─ 岗位空闲 → DISPATCHED → 执行中
       └─ 岗位忙碌 → QUEUED → DISPATCHED → 执行中

普通执行结束 → AWAITING_REVIEW → 验收通过 → DONE
计划生成结束 → AWAITING_APPROVAL → 用户批准 → 执行 → 验收
```

仅保存编辑内容不自动启动执行。用户明确点击“确认再次发起”后才进入新一轮，避免一次普通编辑产生执行费用或文件改动。

再次发起成功进入队列或取得执行资格时：

- 清除任务卡当前的 `completedAt`、`reviewedAt`。
- 将上一轮验收信息保存在本轮续接记录中。
- 本轮修改要求独立保存，不继续复用 `reviewNote` 作为修改要求字段。
- 历史 `TaskRun.completedAt` 等信息保持原值。

提交失败、尚未接受执行请求时，任务继续保持原状态和完成信息。

### 2.2 已完成任务的操作入口

在已完成任务卡和详情抽屉增加“再次发起”。

用户操作顺序：

1. 打开已完成任务。
2. 可先点击“编辑”，修改并保存需求。
3. 点击“再次发起”，进入现有详情抽屉中的续接区域。
4. 填写“本轮修改要求”。
5. 查看提示：将复用历史结果和产物，并沿用当前工作模式。
6. 点击“确认再次发起”。

交互规则：

- 修改要求可留空；留空时使用当前保存的需求继续执行。
- 已编辑但未保存的内容不得直接派发，应先保存或明确放弃编辑。
- 提交期间禁用按钮，避免连续点击。
- `DISPATCHED`、`RUNNING`、`QUEUED` 状态不允许修改执行输入。
- 取消编辑或关闭抽屉不改变任务状态。
- 原有只读设置、知识检索设置、计划批准流程继续生效。
- 计划模式再次发起时，重新生成方案并等待批准，不直接使用旧方案执行新需求。

正常续接的文案使用“历史结果”“本轮修改要求”“在已有产物基础上继续”，只有验收打回时才显示“打回原因”。

### 2.3 上下文复用方式

**推荐首期采用“新执行会话＋历史上下文”，支持跨执行平台继续工作。**

本轮上下文按以下顺序组装：

| 内容 | 来源与规则 |
| --- | --- |
| 当前需求、验收标准及权限 | 当前已保存的任务字段，作为本轮执行依据 |
| 本轮修改要求 | 用户此次提交的说明 |
| 历史执行结果 | 同一任务最近若干轮有效摘要，标记成功、失败及计划结果 |
| 历史验收意见 | 明确标为历史反馈，避免与本轮要求混淆 |
| 既有产物 | 同一任务登记的产物清单，包含名称、类型、路径和可用性 |
| 必要历史消息 | 从关联运行的会话中读取用户要求与最终答复，作为补充资料 |

具体约束：

- 当前需求、本轮修改要求和当前权限优先于历史指令。
- 历史内容标明为参考资料，不允许其中的旧授权扩大当前执行权限。
- 不把工具日志、系统注入规则、凭证或整份原始会话复制到提示词。
- 初始限制为最近 5 轮有效摘要、最多 20 条必要历史消息；补充历史文本总量限制为 20,000 字符。
- 产物优先带入本轮修改要求引用的路径，再带入最近相关产物；超过限制时明确显示省略数量。
- 必要产物没有进入提示词时，通过任务产物清单查询能力补查，避免默默丢失。
- 历史会话不可读取时，降级使用摘要、验收意见和产物引用，并显示“历史会话不可用，已使用摘要续接”。
- 不自动读取全部产物内容；执行岗位根据本轮需求读取相关文件。
- 本地产物检查仍遵循现有仓库路径边界；外部链接只作为引用，不自动访问。

不默认使用原 CLI 会话恢复，主要考虑两个执行平台的恢复方式、权限处理和消息归属存在差异。上述方式可以复用已保存业务结果，也便于切换平台。

**待确认：这里的“上下文继续用”是否接受上述历史上下文复用方式？本方案默认接受；如果必须完整恢复原 CLI 会话，需要追加会话恢复及权限验证范围。**

### 2.4 排队时保存本轮派发参数

保留现有“任务排队、岗位空闲后创建运行”的流程，增加持久化派发参数，避免重构整个调度机制。

建议增加：

| 对象 | 字段 | 用途 |
| --- | --- | --- |
| `Task` | `pendingDispatch Json?` | 保存排队中的平台、模式、修改要求、上下文来源、提交时间及原状态信息 |
| `TaskRun` | `dispatchContext Json?` | 保存本轮修改要求、上下文来源 ID、截断或降级状态、上一轮验收信息等续接依据 |

处理规则：

1. 在现有事务与状态版本检查下接受派发请求。
2. 岗位忙碌时，完整保存 `pendingDispatch` 并进入 `QUEUED`。
3. 自动推进时读取已保存参数，禁止重新使用默认平台或丢弃修改要求。
4. 实际启动前重新采集工作区基线，排队等待期间的文件变化不算本轮成果。
5. 创建运行并确认接管后，将对应上下文写入 `dispatchContext`，清除待派发参数。
6. 取消排队时清除待派发参数。
7. 队列中的任务禁止编辑执行输入，确保提交内容与实际执行一致。
8. 使用现有岗位锁和任务版本检查防止重复启动；自动推进重试不得重复创建有效运行。

`dispatchContext` 不保存完整提示词、完整会话或文件正文。

### 2.5 既有产物的保留与本轮归属

继续使用任务级 `TaskArtifact`，再次发起时不删除已有产物。

为区分本轮交付，建议增加可空字段：

- `TaskArtifact.lastRunId`：最后一次明确登记或更新该产物的运行 ID，关联 `TaskRun`，删除运行时设为空。

登记规则：

- 新路径：新增产物记录并关联本轮运行。
- 已有路径再次被明确交付或检测到内容变化：更新本轮关联，不重复插入。
- 已有路径没有被本轮确认或修改：保留为历史产物。
- 手动添加、缺少运行来源的产物：显示“手动登记”或“历史来源未记录”。
- 本地文件已缺失：保留记录并提示不可用，不直接删除。
- 同一路径的内容继续指向当前工作区文件，本期不提供历史文件版本下载。

同时修正与再次发起直接相关的文件检测问题：现有快照主要比较 Git 状态码，同一文件连续两轮都为 `M` 时可能漏记更新。对纳入检测的文件增加内容指纹，识别“状态相同但内容变化”，并兼容旧基线数据。

详情展示区分：

- **全部产物**：任务持续积累的产物。
- **本轮交付**：本轮明确登记或更新的产物。
- **历史产物**：保留供继续使用的既有成果。

验收时，如果只有历史产物、没有本轮交付，要求填写本轮完成说明或确认沿用哪些历史成果，避免直接凭旧产物数量通过新一轮验收。

当前任务派发固定在数字团队仓库执行，因此首期项目来源使用服务端已确认的仓库信息，不新增任意路径输入。

| `projectName String?` | 派发时记录展示名称，当前显示“个人数字团队” |

页面调整：

- 交付统计先按项目汇总，再展开现有 `api/`、`web/`、`agents/` 等目录明细。

统计口径明确区分：

| 指标 | 统计方式 |

| 同文件多轮修改 | 每轮均可计入对应运行，页面标注为“按运行累计” |
| 无 Git 统计的链接或报告 | 可计入产物数量，不编造增删行数据 |

“没有采集到统计”和“已采集且没有变化”应分别展示，不能统一解释为零。

## 6. 风险与回滚

### 6.1 风险及控制

| 风险 | 控制方式 |
| --- | --- |
| 再次发起覆盖旧验收依据 | 接受请求前保存历史验收信息，保留原运行记录 |
| 排队后修改要求丢失 | 持久化待派发请求，禁止推进时使用默认值重建 |
| 历史指令扩大本轮权限 | 历史资料明确降级为参考，当前权限和工作模式优先 |
| 会话中包含不适合复用的内容 | 不复制整份原始会话，不注入工具日志和凭证 |
| 历史产物已删除或被覆盖 | 检查可用性并提示；说明本期没有文件内容版本备份 |
| 新旧产物混淆导致错误验收 | 区分本轮交付与历史产物，纯沿用场景要求说明 |
| 已有脏文件的再次修改漏记 | 增加内容变化检测，并保留显式产物登记 |
| Git 行数不能准确反映每轮实际编辑量 | 标注现有净差额统计口径，不据此宣称真实工作量 |
| 历史项目归属不可靠 | 显示未知，不自动回填 |
| 数据结构变化导致兼容问题 | 新字段可空，保留旧接口字段，先验证旧数据读取 |

### 6.2 回滚步骤

1. **暂停新入口。** 若发现重复执行、权限或队列参数问题，先关闭再次发起入口，防止新增请求。
2. **处理已接受的任务。** 核对正在运行和排队的任务；旧版本不会读取新增待派发参数，回退前必须暂停或妥善取消这些排队请求。
3. **回退前后端代码。** 回到本次修改前的版本，保留已产生的任务、运行、日志和产物记录。
4. **保留新增数据库字段。** 本次采用加法迁移，代码回退时优先保留可空字段，避免删除续接依据。
5. **恢复展示。** 项目分组若有问题，可先回到原目录统计，不影响任务和产物读取。
6. **核对状态。** 确认没有已退出进程仍显示运行中、重复启动或无法处理的队列任务。
7. 如确需删除新增字段，先备份并确认没有使用方，再单独执行反向迁移。

代码回滚不会自动恢复任务执行过程中被修改的业务文件。文件恢复应依据对应仓库的提交或备份处理，不使用整体工作区重置，以免覆盖用户其他改动。
